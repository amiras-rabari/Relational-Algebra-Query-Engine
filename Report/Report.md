# 1. System & Architecture Setup

## 1.1 System Components

- **Tokenizer & Parser:** Hand-written character-by-character scanner (maximal munch) and recursive-descent parser generating an Abstract Syntax Tree (AST). No regular expression or parser generator libraries were used.
- **Execution Strategy:** Bottom-up evaluation of the AST without query optimization or algebraic rewriting. The tree is executed strictly as specified in the input query.
- **Join Algorithm:** Standard $O(N_R \times N_S)$ Tuple-at-a-Time Nested Loop Join.
- **Instrumentation Counters:** Exact, non-estimated counters placed directly inside operator loops:
    - `joinComparisonCount`: Incremented on every tuple pair evaluated inside the join inner loop, regardless of whether the join predicate evaluates to `true` or `false`.
    - `selectTupleCount`: Incremented on every single tuple evaluated inside the `select` predicate loop.

# 2. Schema and Benchmark Data Setup

The benchmark uses two synthetic relations generated by a custom data generator tool. Data types consist of bare/quoted strings and integers.

## 2.1 Relation Schemas

  **R Table** ($R(a, b)$)**:**
    ◦ `a` (Integer) — Unique primary attribute / identifier ($1, 2, \dots, N_R$)..
    ◦ `b` (Integer) — Foreign key join attribute referencing $S.b$.

 S **Table** ($S(b, c)$)**:**
    ◦ `b` (Integer) — Primary key join attribute.
    ◦ `c` (Integer) — Unique payload attribute ($100001, 100002, \dots$).

*Note: Attributes are natively prefixed by table scope (`R.a`, `R.b`, `S.b`, `S.c`), eliminating the need for explicit `rename` operators during join execution.*

## 2.2 Data Generator Parameters

- **Tuple Scale** ($N = M$)  : Evaluated at $N \in \{1000, 2000, 4000, 8000, 16000, 32000, 64000\}$

- **Match Rate:** Set to `1.0` for 1-to-1 matching semantics (yielding $N$ output tuples) or `2.0` for 1-to-many fan-out testing (yielding $2N$ output tuples).

## Questions

### **1. Relationship between n, m and the comparison count.**

comparisons = n × m. The join is a nested loop and the counter is incremented once per pair, before the condition is evaluated, so it counts every pair whether or not it matches. There is no early exit anywhere, which is why the count is exact. For n = m = 1000 I got 1,000,000, and for 64000 I got 4,096,000,000, which equals 64000². The measured count matched the formula exactly at all seven sizes, so there is no discrepancy to explain. 

### **2. Slope on log-log axes.**

**Analysis:**
Taking the log-log transformation of $T(n) = c \cdot n^k$ yields:

$$
\log(T) = k \cdot \log(n) + \log(c)
$$

 Using the two largest measured data points ($N_1 = 32,000$, $N_2 = 64,000$):

$\Delta \log(N) = \log_{10}(64000) - \log_{10}(32000) = \log_{10}(2) \approx 0.30103$

$\Delta \log(T) = \log_{10}(2857.81) - \log_{10}(691.663) = \log_{10}(4.1317) \approx 0.61613$

$\text{Slope } k = \frac{0.61613}{0.30103} \approx 2.046$

A slope of $\approx 2.05$ confirms quadratic growth ($O(n^2)$).

A slope of 2 means time grows as n². Since n = m, this is the n × m behavior of a nested loop: the work is one condition evaluation per pair, and that number is fixed by the input sizes, not by the data. Small sizes can sit a little off the line because the run is so short that timer resolution and cache warm-up matter. 

### **3. Select and project compared with join.**

**Select :** examines each input tuple exactly once  ($O(n)$ complexity) , so its counter equals n (4,000 to 32,000, exactly) and its time grows linearly, with a slope of about

 $\approx 1.0$ ($16k \rightarrow 32k$ increases time from $0.0117\text{ s}$ to $0.0227\text{ s}$, a $1.94\times$ change).

 **Join:** Evaluates all tuple pairs ($O(n^2)$ complexity), yielding $n \times m$ comparisons with a log-log slope of $2.0$

**Project :**  is different from both. It removes duplicates by scanning the output built so far for every input tuple. For `project[b](R)` all n values are distinct, so the scan grows with the output and the total comparisons equal:

$$
\text{Comparisons} = \frac{n(n-1)}{2} \approx O(n^2)
$$

My measured slope was about  is $\approx 2.0$ ($16k \rightarrow 32k$  increases time from $13.33\text{ s}$ to $53.53\text{ s}$, a $4.01\times$ change). It is quadratic like the join, but with a smaller constant: about half as many comparisons, and each one stops at the first differing value, with no column lookup and no combined-tuple building. So project is not linear in my implementation. Its cost depends on the number of distinct output tuples, roughly n × (distinct outputs). It only looks linear when the projected column has few distinct values.

### **4. Predicted time for one million tuples per side.**  ($N = M = 1,000,000$)

- Total Comparisons: $10^6 \times 10^6 = 10^{12}$ comparisons.
- From my largest measurement  (at $N=64,000$):
    
    $$
    \text{Cost/comp} = \frac{2857.81\text{ s}}{4,096,000,000} \approx 6.977 \times 10^{-7}\text{ s} \quad (697.7\text{ ns})
    $$
    
- Predicted time:.

$$
\text{Time} = 10^{12} \times 6.977 \times 10^{-7}\text{ s} = 697,700\text{ seconds}

$$

$$
\text{Time} \approx 193.81\text{ hours} \approx 8.07\text{ days}
$$

- Verification via Quadratic Scaling Factor:

$$
\text{Scaling Factor} = \left(\frac{1,000,000}{64,000}\right)^2 = 15.625^2 = 244.140625
$$

$$
\text{Predicted Time} = 2857.81\text{ s} \times 244.140625 = 697,707\text{ s} \quad (\approx 8.07\text{ days})
$$

### **5. Effect of the match rate.**

I   did comparing runs at scale $N=8000, M=8000$: 

**Match Rate 0.5:** $64,000,000$ comparisons,  $40.6205\text{ s}$ wall time ($4,000$ outputs)

**Match Rate 1.0:** $64,000,000$ comparisons,  $40.6205\text{ s}$ wall time ($8,000$ outputs)

The comparison count did not change: it was 64,000,000 every time, because it is n x m regardless of how many pairs match. The wall time changed only slightly: between 39.136 s (Rate 1.0) and 40.620 s (Rate 0.5). The two answers differ only slightly because the only match-dependent work in the join is building a combined tuple (a heap allocation) for the pairs that match, and that costs on the order of the output size. With matchRate 1.0 there are only n outputs against n² comparisons, so the extra work is about 1/n of the total and disappears in the noise. Every comparison, matching or not, pays the same cost of resolving both columns and comparing the values.

### **6. What I would change to make the million-tuple join feasible.**

The problem is the algorithm, not the constants: 10¹² condition evaluations cannot be done in reasonable time. For an equality join like R.b = S.b I would replace the nested loop with a hash join: 

Hash Join ($O(n + m)$):

Build an in-memory hash table on $S.b$ ($O(m)$ work).

Probe the table for each tuple in $R$ ($O(n)$ work).

Reduces total operations from $10^{12}$ to $\sim 2 \times 10^6$, dropping execution time from days to sub-second

Sort-Merge Join ($O(n \log n + m \log m)$):

Sort both relations on the join attribute and merge matching keys in a single pass.

Hash Set Duplicate Elimination for Project ($O(n)$):

Replace linear-scan duplicate removal in `project` and set operators with an $O(1)$
hash set lookup, reducing projection from $O(n^2)$ to $O(n)$.

Column Offset Caching:

Cache attribute index positions prior to execution rather than performing dynamic string-based column name lookups inside inner evaluation loops.
